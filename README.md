# NOVA MARKAT

منصة تجارة إلكترونية جزائرية متعددة الأدوار، بواجهة عربية من اليمين إلى اليسار وخلفية Django. تدعم حسابات المشترين والبائعين والموردين وشركات التوصيل، مع إدارة المنتجات والمخزون والطلبات والإشعارات. طريقة الدفع المتاحة حاليًا هي **الدفع عند الاستلام**؛ لا توجد بوابة دفع إلكتروني مفعّلة.

## مكونات المشروع

- `config/`: إعدادات Django والمسارات.
- `store/`: النماذج، النماذج التفاعلية، منطق المتجر وواجهات API والاختبارات.
- `templates/`: صفحات HTML المولّدة من Django.
- `static/`: ملفات CSS والشعار والأصول الثابتة.
- `build.sh`: تثبيت المتطلبات، فحوصات Django، جمع الملفات الثابتة وتطبيق **الترحيلات المحفوظة في Git فقط**.
- `render.yaml`: وصف خدمة Render ومتغيرات البيئة المطلوبة.
- `netlify/redirects-production` و`netlify/redirects-staging`: وجهتا الوكيل المنفصلتان للإنتاج والاختبار.

## التشغيل المحلي

يتطلب Python 3.12 أو إصدارًا متوافقًا مع المتطلبات.

```bash
python -m venv .venv
# Windows:
.venv\\Scripts\\activate
# Linux/macOS:
source .venv/bin/activate
python -m pip install -r requirements.txt
```

اضبط متغيرات البيئة قبل تشغيل Django:

- `SECRET_KEY`: مفتاح عشوائي خاص بالبيئة؛ لا تضعه في Git.
- `DEBUG`: استخدم `True` للتطوير المحلي فقط، و`False` للنشر.
- `ALLOWED_HOSTS`: أسماء المضيفين المسموح بها مفصولة بفواصل.
- `DATABASE_URL`: رابط قاعدة البيانات؛ مطلوب في الإنتاج ولا ينبغي أن يشير الاختبار إلى قاعدة بيانات الإنتاج.
- `CSRF_TRUSTED_ORIGINS`: الأصول الموثوقة عند الحاجة، مفصولة بفواصل.

ثم نفّذ:

```bash
python manage.py check
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

افتح `http://127.0.0.1:8000/`. لا يتضمن المشروع بيانات منتجات تجريبية تُنشأ تلقائيًا؛ أضف الفئات والمنتجات من لوحة الإدارة بعد إعداد حساب إداري. لا تستخدم بيانات عملاء حقيقية في الاختبارات.

## API المتاحة حاليًا

- `GET /api/csrf/`: الحصول على رمز CSRF.
- `GET /api/products/`: المنتجات النشطة المتوفرة في المخزون.
- `GET /api/delivery-companies/`: شركات التوصيل المعتمدة.
- `GET /api/cart/`: قراءة سلة الجلسة.
- `POST /api/cart/`: تحديث السلة بعد التحقق من المعرفات والكميات والمخزون.
- `POST /api/cart/add/<id>/`: إضافة منتج إلى السلة.

طلبات تغيير الحالة تخضع لحماية CSRF. يجب أن تتحقق الواجهة من الاستجابة الفعلية للخادم، ولا تعتبر السلة طلبًا مؤكّدًا إلا بعد إتمام مسار الدفع عند الاستلام بنجاح.

## النشر

### Render — الخلفية

1. اربط الخدمة بمستودع GitHub والفرع المقصود.
2. استخدم أمر البناء `./build.sh` وأمر التشغيل `gunicorn config.wsgi:application`.
3. عيّن `SECRET_KEY` و`DEBUG=False` و`DATABASE_URL` و`ALLOWED_HOSTS` و`CSRF_TRUSTED_ORIGINS` حسب البيئة.
4. تحقّق من أن خدمة الاختبار تستخدم قاعدة بيانات اختبار مستقلة تمامًا؛ لا توجّهها إلى قاعدة بيانات الإنتاج.
5. راجع سجلات البناء والترحيلات وفحوصات الصحة قبل وبعد النشر.

### Netlify — واجهة الوكيل

يُستخدم `netlify.toml` لنشر قواعد إعادة التوجيه. ملف الإنتاج يوجّه إلى الخلفية الحية الحالية، وملف الاختبار يوجّه إلى خدمة الاختبار المعزولة. لا تغيّر وجهة الإنتاج إلى خدمة أخرى قبل التحقق من إعداداتها وقاعدة بياناتها.

## فحوصات CI

سير العمل `.github/workflows/django-checks.yml` يشغّل فحوصات Django، وفحوصات الأمان، وجمع الملفات الثابتة، والترحيلات على قاعدة اختبار مؤقتة، والاختبارات، وفحص انحراف الترحيلات، ثم اختبارًا دخانيًا لوجهة الاختبار.

نجاح CI والاختبار الدخاني لا يثبت وحده أن تسجيل الحساب والشراء وكل تكاملات الإنتاج سليمة؛ يلزم اختبار قبول نهائي بعد الموافقة على الإصدار.

## قائمة ما قبل الإصدار

- [ ] التأكد من الفصل الفعلي بين قاعدة بيانات الاختبار والإنتاج.
- [ ] مراجعة انتهاء صلاحية قاعدة البيانات وخطة الاستمرار قبل تاريخ الانتهاء.
- [ ] التأكد من إعدادات الأسرار والمضيفين وCSRF وعدم إظهار الأسرار في السجلات أو المستودع.
- [ ] اختبار التسجيل والدخول وصلاحيات الأدوار واعتماد البائعين.
- [ ] اختبار إضافة المنتج وتحديث المخزون والسلة والطلب ببيانات اختبار.
- [ ] اختبار الموقع المباشر وملفات CSS والشعار وملف PWA ومسارات API وسجلات الخادم.
- [ ] أخذ نسخة احتياطية قابلة للاستعادة قبل أي تغيير إنتاجي مؤثر.

**الحالة:** نجاح الاختبارات الآلية لا يعني أن الإصدار الإنتاجي قد نُشر أو أنه جاهز لاستقبال بيانات العملاء. لا تنفّذ الدمج أو النشر النهائي دون موافقة صريحة ومراجعة عناصر قائمة الإصدار أعلاه.
